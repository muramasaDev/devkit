# UI Pattern Decision Framework

- 역할: 사용자 요청과 프로젝트 맥락에서 패턴 후보를 좁히는 기준
- 값 정본: `defaults.md` (본문의 DF-nn 은 그 표의 항목 번호)
- 아래 표는 출발점이고 절대 규칙이 아님. 후보의 상세 파일에서 When to Use 및 When Not to Use 를 확인한 뒤 확정한다
- 원칙: 사용자의 목적에 필요하지 않은 패턴은 적용하지 않는다. 기존 화면의 같은 상황에 이미 쓰는 패턴이 있으면 그것을 따른다

## 1. 먼저 확인할 것 (10가지)

| No | 확인 항목 | 확인 방법 | 결정에 미치는 것 |
|---|---|---|---|
| 1 | 프로젝트 목적 및 핵심 사용자 | README, 요구 문서, 사용자에게 질문 | 정보 밀도, 용어, 숙련도 가정 |
| 2 | 사용자 행동 및 작업 흐름 | 라우트, 화면 목록, 주요 동작 | 화면 순서, 주 행동 하나 |
| 3 | 플랫폼 및 디바이스 | 프레임워크, 뷰포트 설정, 터치 여부 | 제스처, 탭바 대 사이드바, 목표 크기 |
| 4 | 기존 정보 구조 및 화면 구성 | 내비게이션 컴포넌트, 레이아웃 파일 | 새 화면의 위치, 이동 패턴 |
| 5 | 인터랙션의 중요도 및 빈도 | 되돌릴 수 있는가, 하루에 몇 번 하는가 | 확인 절차의 무게, 단축 수단 |
| 6 | 데이터 복잡도 및 처리 상태 | API 응답 형태, 소요 시간, 진행률 제공 여부 | 로딩 패턴, 목록 탐색 패턴 |
| 7 | 오류 가능성 및 복구 방법 | 검증 규칙, 실패 응답, 재시도 가능 여부 | 오류 표시 위치, 되돌리기 |
| 8 | 기존 디자인 시스템 및 컴포넌트 | 컴포넌트 폴더, 토큰 파일, UI 라이브러리 의존성 | 재사용 대상, 새로 만들 범위 |
| 9 | 접근성 및 반응형 요구 | 기존 ARIA 사용, 중단점, 요구 문서 | 대체 수단, 화면 크기별 패턴 |
| 10 | 유지보수성 및 구현 복잡도 | 팀 규모, 기존 코드 방식 | 단순한 패턴 우선 |

- 코드에서 확인할 수 없고 결정이 갈리는 항목만 사용자에게 묻는다. 나머지는 기본값을 정하고 보고에 적는다

## 2. 상황별 후보

### 알림 및 확인
| 상황 | 1순위 후보 | 대안 | 고르는 기준 |
|---|---|---|---|
| 작업 성공을 알림 (추가 행동 없음) | FB-01 Toast | 그 자리의 상태 변화만 | 결과가 화면에 이미 보이면 알림 생략 |
| 방금 한 일을 되돌릴 수 있음 | FB-02 Snackbar | 없음 | 되돌릴 수 있으면 사전 확인보다 실행 후 되돌리기 |
| 되돌릴 수 없거나 비용이 큰 결정 | FB-04 Modal dialog | 전용 확인 화면 | 결과를 문구에 구체적으로 적을 수 있을 때 |
| 화면 전체에 걸친 지속 안내 | FB-03 Banner | ES-04 Offline state | 사용자가 닫거나 상황이 끝날 때까지 유지 |
| 입력 검증 오류 | FB-06 Inline error | 폼 위 오류 요약 추가 | 오류는 필드 옆에. 필드가 많으면 요약 병행 |
| 필드에 속하지 않는 제출 실패 (서버 오류 등) | 폼 위 오류 문구 (`role="alert"`, 카탈로그 외) | FB-03 Banner | 입력한 값 유지, 다시 시도 가능. 브라우저 `alert()` 는 쓰지 않음 |
| 항목에 딸린 보조 행동 묶음 (모바일) | FB-05 Bottom sheet | 메뉴 (데스크톱) | 화면 크기에 따라 전환 |
| 용어 및 수치의 보충 설명 | FB-07 Tooltip | 본문에 직접 표기 | 꼭 필요한 정보는 툴팁에 숨기지 않음 |
| 새 기능 위치 안내 | FB-08 Coach mark | ES-01 First use empty state | 한 번에 하나, 다시 띄우지 않음 |
| 읽지 않은 수 및 새 항목 표시 | FB-09 Badge | 없음 | 숫자가 뜻이 있을 때만 숫자 |

### 로딩 및 진행
| 상황 | 1순위 후보 | 대안 | 고르는 기준 |
|---|---|---|---|
| 모양이 정해진 콘텐츠의 첫 로딩 | LD-02 Skeleton | LD-01 Spinner | 결과 배치를 미리 알면 스켈레톤 |
| 짧고 모양을 모르는 대기 | LD-01 Spinner | 표시 없음 | 아주 짧게 끝나면 표시가 번쩍이지 않게 지연 후 표시 |
| 진행률을 실제로 측정할 수 있는 작업 | LD-03 Progress bar | LD-04 Progress ring | 좁은 자리는 링. 측정 불가면 스피너 |
| 여러 단계 입력 | LD-05 Step indicator | 한 화면 폼 | 단계가 3개 이상이고 순서가 있을 때 (DF-30) |
| 단추를 눌러 제출 | LD-06 Button loading | LD-01 Spinner | 누른 자리에서 처리 중 표시 및 중복 실행 방지 |
| 실패가 드물고 되돌리기 쉬운 동작 | LD-08 Optimistic update | LD-06 Button loading | 결제 등 결과가 중요한 동작에는 쓰지 않음 |
| 큰 이미지 | LD-07 Progressive image | LD-02 Skeleton | 저해상도 미리보기를 만들 수 있을 때 |
| 페이지 이동 대기 | LD-09 Top loading bar | LD-02 Skeleton | 이전 화면을 유지한 채 이동 중임을 알릴 때 |
| 검색어 및 필터를 바꿔 목록을 다시 불러옴 | 기존 목록 유지 및 영역 `aria-busy` (카탈로그 외), LD-09 | LD-02 Skeleton | 늦게 도착한 이전 요청의 응답은 버림. 실패하면 기존 목록을 두고 오류 문구 및 다시 시도 |

### 빈 화면 및 시스템 상태
| 상황 | 후보 | 고르는 기준 |
|---|---|---|
| 처음 써서 자료가 없음 | ES-01 | 시작 행동 하나. 사용자가 채우는 목록이 아니면 이유만 표시 |
| 검색어에 맞는 것이 없음 | ES-02 | 검색어 표시 및 다른 검색 제안 |
| 필터 조건에 맞는 것이 없음 | ES-03 | 적용된 조건 표시 및 초기화 |
| 검색어 및 필터가 함께 걸려 0건 | ES-02 및 ES-03 을 한 화면에 | 검색어 및 조건을 모두 보여 주고 `필터 초기화` 및 `검색어 지우기` 를 각각 제공 |
| 연결 끊김 | ES-04 | 불러오기 실패(ES-08)와 구분 |
| 기능에 OS 권한이 필요 | ES-05 | 이유를 먼저 알림. 반복 요청은 DP-09 |
| 할 일을 모두 끝냄 | ES-06 | 긍정 표시로 끝냄 |
| 방금 비움 | ES-07 | 되돌리기 가능하면 FB-02 병행 |
| 불러오기 실패 | ES-08 | 원인을 알면 적고 다시 시도 제공 |
| 조건 충족 전 이용 불가 | ES-09 | 여는 조건을 적음 |

### AI 화면
| 상황 | 후보 | 고르는 기준 |
|---|---|---|
| 응답 시작 전 대기 | AI-01 | 내부 상태를 모르면 상태만 표시 |
| 응답 생성 | AI-02 | 스트리밍 API 가 있을 때. 정지 수단 포함 |
| 무엇을 물을지 모르는 첫 화면 | AI-03 | ES-01 의 AI 화면판 |
| 답이 마음에 들지 않음 | AI-04, AI-07 | 같은 질문 재시도는 AI-04, 질문 수정은 AI-07 |
| 사실 주장에 근거가 있음 | AI-05 | 백엔드가 출처 정보를 응답에 주는지 먼저 확인. 실제로 쓴 출처만 |
| 품질 신호 수집 | AI-06 | 수집한 신호를 실제로 쓸 때만 |
| 문서 및 이미지를 입력으로 | AI-08 | 올리는 중, 올리기 완료, 처리 중, 실패, 제거 상태 포함 |
| 여러 도구 및 단계를 수행 | AI-09 | 실제 실행 이벤트가 있을 때만 단계 표시 |

### 이동 구조
| 상황 | 1순위 후보 | 대안 | 고르는 기준 |
|---|---|---|---|
| 모바일 최상위 목적지가 적고 자주 오감 | NV-01 Tab bar | NV-03 Drawer | 목적지가 더 많거나 덜 쓰이면 드로어 |
| 한 화면 안의 분류 | NV-02 Top tabs | FM-03 Segmented control | 내용 전환은 탭, 보기 방식 전환은 세그먼트 |
| 깊은 계층에서 현재 위치 | NV-04 Breadcrumb | NV-09 Back navigation | 계층이 3단계 이상인 웹 (DF-31) |
| 긴 화면에서 맥락 및 주 행동 유지 | NV-05 Sticky header | 없음 | 화면 높이를 과하게 차지하지 않을 때 |
| 화면의 주 행동 하나 | NV-06 Floating action button | 헤더의 단추 | 화면당 하나 |
| 목록 탐색 (찾기, 위치 복귀 필요) | NV-07 Pagination | NV-08 + `더 보기` | 검색 결과, 표, 관리 화면 |
| 목록 훑어보기 | NV-08 Infinite scroll | NV-07 | 피드. 푸터 및 위치 복원 문제 확인 |

### 입력
| 상황 | 후보 | 고르는 기준 |
|---|---|---|
| 하나 고르기, 선택지가 2개에서 5개이고 모두 보여야 함 (DF-32) | FM-06 Radio button, FM-03 Segmented control | 폼 안은 라디오, 보기 전환은 세그먼트 |
| 하나 고르기, 선택지 많음 | FM-02 Select | 아주 많으면 검색 가능한 입력 검토 |
| 여러 개 고르기 | FM-05 Checkbox | 제출 시 적용 |
| 켜고 끄기, 즉시 적용 | FM-04 Switch | 제출 단추가 있는 폼이면 체크박스 |
| 범위 안의 대략적인 값 | FM-07 Slider | 정확한 값이 필요하면 숫자 입력 병행 |
| 작은 정수의 증감 | FM-08 Stepper | 범위가 넓으면 숫자 입력 |
| 날짜 | FM-09 Date picker | 오늘과 가까운 날짜. 생년월일처럼 먼 과거는 년, 월, 일 직접 입력이 우선 |

## 3. 후보 비교 기준
후보가 둘 이상 남으면 아래 7가지로 비교하고, 보고에 고른 이유를 한 줄로 적는다

| 기준 | 묻는 것 |
|---|---|
| 사용성 | 목적을 더 적은 단계로 끝내는가 |
| 명확성 | 무슨 일이 일어났고 다음에 무엇을 하는지 드러나는가 |
| 정보 밀도 | 화면 및 사용자 숙련도에 맞는 양인가 |
| 접근성 | 키보드, 스크린 리더, 단일 포인터로 같은 일을 할 수 있는가 |
| 작업 효율성 | 자주 하는 작업을 막지 않는가 (모달 남용 등) |
| 일관성 | 같은 상황에 기존 화면이 쓰는 패턴과 같은가 |
| 성능 및 구현 복잡도 | 기존 컴포넌트로 되는가, 새 의존성이 필요한가 |

- 충돌 시 우선순위: 접근성 및 윤리적 UX (다크 패턴 금지) > 기존 UI 와의 일관성 > 명확성 > 효율성 > 시각 효과
- 기존 UI 가 접근성 기준을 어기는 경우: 작업 범위 안에서 새로 만들거나 고치는 부분은 일관성보다 접근성이 우선이고, 범위 밖의 위반은 고치지 않고 보고한다
- 카탈로그에 없는 요소(표, 차트, 지표 카드, 비밀번호 입력 등)는 패턴 ID 를 지어내지 않고 `카탈로그 외` 로 적은 뒤 4절 인터랙션 규칙, `accessibility.md`, `responsive-design.md` 로 설계한다. 차트처럼 전용 지침이 따로 있는 영역은 그 지침을 따른다

## 4. 인터랙션 규칙 (모든 패턴 공통)
- 사용자 액션에는 즉각적인 피드백을 준다 (눌림 표시, 상태 변화, 로딩 표시 중 하나)
- 처리 중에는 같은 동작의 중복 실행을 막는다 (단추 비활성 또는 요청 중복 제거)
- 실패하면 원인과 복구 방법(다시 시도, 고칠 곳)을 함께 알린다
- 파괴적인 작업은 실행 후 되돌리기(FB-02) 또는 사전 확인(FB-04) 중 하나를 둔다. 되돌릴 수 있으면 되돌리기가 우선
- 비활성 상태는 모양으로 구분되게 하고, 왜 비활성인지 알 수 있게 한다
- 키보드 및 터치 양쪽으로 같은 일을 할 수 있게 한다
- 움직임은 상태 변화를 이해시키는 용도로만 쓴다 (`motion.md`)

## 5. 적용하지 않는 판단
- 결과가 화면에 이미 드러나는 동작에 토스트를 더하지 않는다
- 되돌릴 수 있는 동작에 확인 모달을 두지 않는다
- 한 번에 끝나는 짧은 폼에 단계 표시를 두지 않는다
- 요청에 없는 온보딩, 코치마크, 애니메이션을 넣지 않는다
- 데스크톱에서 터치 전용 제스처에 의존하지 않는다
