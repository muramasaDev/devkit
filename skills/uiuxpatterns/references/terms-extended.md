# Extended Terms (확장 용어: 컴포넌트, AI 화면, UX 법칙, 성능 체감)

- 역할: 패턴 90개와 용어집에 이름이 없던 용어를 한곳에 모은 목록. 이름을 몰라 `그거` 라고 부르던 것을 찾는 용도
- 쓰는 법: 화면을 시키거나 검수할 때 이 이름으로 말한다. `우리 쪽` 칸은 가장 가까운 기존 패턴 ID 이다. 같은 뜻의 이름은 5절 동의어 표
- 정의는 직접 쓴 것이다. 공개 디자인 시스템 (WAI-ARIA, GOV.UK, IBM Carbon, Atlassian, GitHub Primer, Apple, Material 안드로이드 문서) 의 컴포넌트 목록과 UX 법칙 모음, AI 화면 가이드라인 (Google PAIR, Microsoft HAX), web.dev 성능 문서를 2026-11-25 에 읽고 이름과 용도를 확인했다
- 읽지 못한 곳: Material Design 3 와 Apple HIG 의 목차 페이지 본문 (대체 자료로 확인), PAIR 메인과 HAX 소개 페이지 (하위 페이지로 확인)

## 2. AI 화면 용어 (17)
| 용어 | 정의 | 화면 설계에서 쓰는 법 | 우리 쪽 |
|---|---|---|---|
| Trust calibration (신뢰 보정) | 잘하는 곳은 믿고 못하는 곳은 직접 판단하도록 사용자의 신뢰 수준을 맞춤 | 위험이 클수록 근거와 재확인 유도를 늘림. 첫 사용 전 한계를 알림 | ai-interfaces 신뢰성 원칙(불확실성 표현만 있음) |
| Confidence display (확신도 표시) | 결과가 얼마나 확실한지 보여 주는 방식. 범주형, 퍼센트, 대안 나열이 있음 | 결정이 달라질 때만 표시. 낮음 구간에는 후보 N개를 나란히 보여 줌 | 없음 (불확실성은 글로만 밝힘) |
| Intent-based outcome specification (의도 기반 결과 지정) | 사용자가 원하는 결과를 말하면 방법은 시스템이 정함. 제어권이 뒤바뀜 | 실행 전 계획 요약과 중간 수정 지점을 둠. 결과를 만든 과정을 볼 수 있게 함 | AI-09 에이전트 단계(패러다임 설명 없음) |
| Context error (맥락 오류) | 시스템은 설계대로 동작했으나 사용자 상황과 안 맞아 오류로 느껴지는 경우 | 왜 이 결과인지 한 줄 설명과 끄기 및 고치기 수단을 같이 둠 | AI 신뢰성 원칙 오류 안내(오류 유형 구분 없음) |
| Automation vs augmentation (자동화 대 증강) | 지루하고 위험한 일은 맡기고, 즐기거나 책임지는 일은 사용자가 쥐고 돕기만 함 | 기능마다 자동 실행인지 제안만인지 정하고 자동은 검토 및 되돌리기를 둠 | AI 신뢰성 원칙 도구 실행 및 승인(승인 기준만 있음) |
| Clarify or scale back (되묻기 또는 기능 축소) | 목표가 모호하면 되묻거나, 확신 없을 때 서비스 수준을 낮춤 | 모호한 요청에 되묻기 질문 1개 또는 안전한 기본 동작만 수행 | 없음 |
| Capability and accuracy disclosure (할 수 있는 일과 정확도 안내) | 시스템이 할 수 있는 것과 얼마나 맞는지를 미리 알림 | 첫 화면에 가능한 일 예시와 한계 문구 한 줄. 정확도는 실측값만 | AI-03 추천 질문 칩(한계 안내 없음) |
| Non-AI fallback (AI 없이 끝내는 길) | AI 가 실패해도 사용자가 다른 방법으로 작업을 끝낼 수 있게 함 | 생성 실패 시 수동 입력 또는 기본 양식으로 이어지는 단추 | AI 신뢰성 원칙 오류 안내(수동 경로 없음) |
| Explanation types (설명 종류: 전체 시스템 대 개별 결과) | 시스템 전반 설명과 이번 결과 하나의 설명을 구분함 | 결과 옆에는 개별 이유, 설정 화면에는 전반 설명 | AI-05 출처 표시(근거 링크만) |
| Articulation barrier (표현 장벽) | 원하는 바를 글로 정확히 쓰기 어려운 사람이 배제되는 문제 | 입력 예시, 칩, 선택형 옵션을 글 입력과 병행 | AI-03 칩과 AI-07 (장벽 개념 없음) |
| Staged onboarding and co-learning (단계별 안내, 함께 학습) | 처음에 모두 설명하지 않고 쓸 때마다 알려 주며, 피드백이 결과를 바꾼다고 보여 줌 | 기능이 처음 필요한 시점에 한 줄 안내, 반영 결과를 다음 화면에 표시 | 없음 |
| Human-like expectation (사람 같은 기대) | 1인칭 대화체가 시스템 능력 이상으로 기대를 키움 | 말투와 캐릭터를 실제 능력에 맞추고 알고리즘임을 밝힘 | 없음 |
| Dismiss and global control (쉬운 무시, 전체 제어) | 원치 않는 제안은 쉽게 끄고, 감시 범위와 동작을 한곳에서 조절 | 제안 닫기 단추, 설정에 AI 기능 켜기 끄기 및 기록 지우기 | dark-patterns DP-09 끝없는 권유(AI 설정 없음) |
| Short-term memory reference (최근 맥락 기억과 참조) | 최근 대화를 기억하고 사용자가 쉽게 가리킬 수 있게 함 | 이전 답변 인용 답장, 현재 기억 중인 항목 목록 및 삭제 | 없음 |
| Capability change notice (기능 변경 알림) | 시스템이 새 능력을 얻거나 동작이 바뀌면 알리고 급변을 피함 | 모델 교체 및 기능 추가 시 변경 사항 한 줄 안내 | 없음 |
| Implicit vs explicit feedback (암묵 및 명시 피드백) | 수락 및 거절 같은 행동 신호와 평점 같은 직접 입력을 구분함 | 수집 사실 고지, 거부 가능, 좋아요 의미를 학습에 쓸지 정함 | 기존과 같음 (AI-06, 암묵 신호 구분만 없음) |
| Context layers (맥락 3층: 전체, 지역, 주변) | 에이전트가 쓰는 정보를 전역 설정, 작업별 입력, 환경 정보로 나눔 | 에이전트 화면에 지금 쓰는 맥락 목록을 보이고 층별로 편집 가능하게 함 | AI-09 에이전트 단계(맥락 표시 없음) |

## 3. UX 법칙 (16)
| 용어 | 정의 | 화면 설계에서 쓰는 법 | 우리 쪽 |
|---|---|---|---|
| Doherty Threshold (도허티 임계) | 응답이 약 0.4초 안이면 사용자와 시스템이 서로 기다리지 않아 작업이 빨라짐 | 0.4초 안에 못 끝나면 중간 결과 또는 낙관적 반영으로 체감 단축 | glossary 낙관적 UI(근거 법칙 없음) |
| Hick's Law (힉의 법칙) | 선택지가 많고 복잡할수록 고르는 시간이 늘어남 | 메뉴와 추천 칩 개수 제한, 주 행동 하나 강조, 단계 나누기 | quality-checklist 1절 주 행동 하나(법칙 이름 없음) |
| Fitts's Law (피츠의 법칙) | 목표가 멀고 작을수록 누르기 어려움 | 자주 쓰는 단추는 크게 엄지 닿는 곳에, 파괴 단추는 멀리 | accessibility.md 목표 크기(법칙 이름 없음) |
| Jakob's Law (야콥의 법칙) | 사용자는 다른 서비스에서 익힌 방식대로 이 화면도 동작하길 기대 | 로그인과 검색과 장바구니 같은 흔한 흐름은 새 방식을 만들지 않음 | 없음 |
| Miller's Law, Chunking (밀러의 법칙, 덩어리 짓기) | 한 번에 기억하는 개수가 한정되어 정보를 묶음 단위로 나눠야 함 | 긴 폼 및 목록을 소제목이 있는 묶음으로 나눔 | forms.md 단계 나누기(법칙 이름 없음) |
| Law of Proximity, Common Region (근접, 공통 영역) | 가깝거나 같은 상자 안에 있으면 한 묶음으로 읽힘 | 관련 필드는 간격을 좁히고 그룹은 테두리 또는 배경으로 묶음 | design-system.md 간격 토큰(묶음 법칙 없음) |
| Peak-End Rule (정점 종결 법칙) | 경험은 가장 강한 순간과 마지막 순간으로 기억됨 | 완료 화면과 오류 복구 화면을 가장 공들여 설계 | glossary 모두 완료 빈 화면(법칙 없음) |
| Goal-Gradient Effect (목표 접근 효과) | 목표에 가까워질수록 더 속도를 냄 | 단계 표시와 진행 바로 남은 거리를 보여 줌. 실제 진행만 표시 | glossary 단계 표시, 진행 바(근거 없음) |
| Cognitive Load (인지 부하) | 화면을 이해하고 쓰는 데 드는 정신 노력 | 한 화면 한 결정, 기본값, 불필요한 장식 제거로 줄임 | 없음 |
| Postel's Law (포스텔의 법칙) | 입력은 폭넓게 받아들이고 출력은 엄격하게 | 전화번호 하이픈 및 공백 허용, 저장은 한 형식으로 정규화 | forms.md 입력 형식(법칙 이름 없음) |
| Tesler's Law (복잡성 보존) | 줄일 수 없는 복잡성은 누군가가 대신 떠안음 | 복잡한 규칙은 시스템 기본값이 처리하고 사용자 입력은 최소화 | 없음 |
| Zeigarnik Effect (자이가르닉 효과) | 끝내지 못한 일이 더 기억에 남음 | 중단된 작성과 업로드를 임시 저장하고 이어 하기 단추 제공 | AI-08 실패 재시도(이어 하기 개념 없음) |
| Von Restorff Effect (고립 효과) | 비슷한 것들 속에서 하나만 다르면 기억됨 | 주 행동 단추 하나만 색 및 크기로 구분, 남발하지 않음 | quality-checklist 5절 행동 위계 |
| Serial Position Effect (순서 위치 효과) | 목록의 처음과 끝이 가장 잘 기억됨 | 중요한 항목을 메뉴 맨 앞과 맨 뒤에 둠 | 없음 |
| Choice Overload (선택 과부하) | 선택지가 너무 많으면 결정을 미루거나 포기함 | 추천 기본값 표시, 목록 단계 나누기, 필터 제공 | 없음 |
| Aesthetic-Usability Effect (미적 사용성 효과) | 보기 좋으면 더 쓰기 쉽다고 평가함 | 검수 시 사용성 문제를 외관 호평으로 덮지 않도록 분리 점검 | 없음 |

## 4. 성능 체감 (5)
| 용어 | 정의 | 화면 설계에서 쓰는 법 | 우리 쪽 |
|---|---|---|---|
| Interaction to Next Paint, INP (다음 화면 갱신까지) | 누르거나 입력한 뒤 화면이 실제로 바뀌기까지 걸린 시간. 느리면 멈춘 것처럼 보임 | 단추 누름에 즉시 눌림 상태를 그리고 무거운 처리는 뒤로 미룸. 기준 200ms 이하 | quality-checklist 4절 즉각 피드백(수치 없음) |
| Cumulative Layout Shift, CLS (배치 밀림) | 로딩 중 내용이 예고 없이 밀려 오조작을 부르는 정도. 기준 0.1 이하 | 이미지와 광고와 늦게 오는 영역의 자리를 미리 잡고 스켈레톤을 같은 크기로 둠 | loading.md 스켈레톤(레이아웃 유지 언급만) |
| Largest Contentful Paint, LCP (주요 내용 표시) | 화면에서 가장 큰 내용이 보이기까지의 시간. 기준 2.5초 이하 | 첫 화면의 큰 이미지 및 제목을 먼저 불러오고 지연 로딩 대상에서 뺌 | 없음 |
| 응답시간 3구간 0.1초, 1초, 10초 | 0.1초는 즉시, 1초는 생각이 이어지는 한계, 10초는 주의가 떠나는 한계 | 1초 넘으면 처리 중 표시, 10초 넘으면 퍼센트와 취소 제공 | glossary 5절 로딩 9종(2초 기준만 있음) |
| TTFB, FCP, TBT (첫 바이트, 첫 표시, 메인 스레드 막힘) | 서버 첫 응답, 첫 내용 표시, 메인 스레드가 막힌 합계 시간. LCP 및 INP 의 원인 진단용 | 체감이 느릴 때 원인이 서버, 렌더 차단, 자바스크립트 중 어디인지 가르는 용도 | 없음 |

- 성능 체감 기준값 (INP 200ms, CLS 0.1, LCP 2.5초) 은 web.dev 문서의 값이다. 바뀔 수 있으니 적용 전에 확인한다
- UX 법칙은 설계의 이유를 설명하는 도구이며 규칙이 아니다. 화면을 바꾸는 근거로 쓸 때는 사용자 시험이나 지표로 확인한다
